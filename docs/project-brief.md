# 项目目标与阶段计划

> 首轮本地 MVP 已完成并验证。以下保留最初目标与阶段规划；实际范围、成果和未完成项以 `STATUS.md`、README 和 `reports/` 为准。当前人工复核、线上试点与云端运行仍未执行。

## 用户目标

为通用 Data Scientist，尤其产品/实验分析相关岗位，完成一个 2–4 周可讲清楚的独立项目。用户对 Text-as-data 感兴趣，希望实际使用 PySpark；Codex 可以承担大部分实现，但用户需要理解关键判断并能够回答面试追问。

## 产品问题

一个电商搜索质量团队需要判断“搜索词与商品是否匹配”。我们先做 ESCI 四分类，再研究：模型把哪些非 Exact 商品误判成 Exact？如果只能检查其中 5% 或 10%，什么复核排序比随机抽查更有用？这些比例是待冻结的实验设计值，不是观察到的业务预算。

复核对象是离线的搜索词—商品配对，预算单位是配对条数。它不等于线上用户数、查询流量、人工工时或节约金额。项目不以自动修改真实搜索排序为首期目标。

## 首期范围

- 数据：官方 ESCI large-version US English 配对及商品元数据；精确规模以实际读取为准。
- 输入：搜索词、商品标题、必要的品牌/颜色/描述字段；从标题和词汇交互起步。
- 模型：多数类基线；一个以词汇匹配特征为输入的简单四分类模型；资源允许时只增加一种有明确动机的改进。
- 数据处理：PySpark DataFrame、Spark SQL、Parquet、可靠的多表关联、聚合与质量检查。
- 分析：类别混淆、查询切片、置信度与错误关系、等预算的复核策略比较。
- 输出：可复现流程、核实过的指标、少量图表、案例分析、一页产品建议和未来线上实验方案。

首期不要求微调大模型、复现获奖集成、全商品库检索、搭建线上服务或云集群。公开基准中的候选商品已有筛选，结果不能直接代表整个商品库的搜索效果。

## 为什么这样设计

基础任务展示 ML；PySpark 和 SQL 展示数据处理；复核预算问题把模型输出连接到实际决策。用户的优势可以体现在标注定义、误差判断和测量有效性。任何“发现了什么”都必须等到实际运行后再写入简历。

数据和通用方法的来源见 [相似项目调研](prior-art.md)。后续新增模型或策略时，记录自己的选择理由和参考来源；不以“没有人做过”作为继续项目的条件。

## 里程碑与验收

| 阶段 | 工作 | 完成证据 |
| --- | --- | --- |
| M0：初始化 | 调研、目标、评估约定、目录 | 当前文档；没有模型结果 |
| M1：数据与基线（第 1 周） | 固定数据版本；小样本验证；全量质量统计；可运行的简单基线 | 来源/哈希清单、实际行数、关联和划分审计、一次可重跑结果 |
| M2：模型与开发评估（第 2 周） | 特征模型；验证集比较；制定测试冻结记录 | 模型和配置、指标定义、开发集案例、冻结清单 |
| M3：错误与复核（第 3 周） | 相同候选池中的等预算抽查；预定义切片；最终测试 | 复核收益/错误召回曲线、按查询重采样的不确定性、限制说明 |
| M4：解释与可展示成果（第 4 周） | 产品备忘录、图表、运行说明、面试练习；必要时云端扩展 | 可复现 README、能追溯至实际实验的结果、用户能解释关键决策 |

两周版本可停在 M2：保留已验证的基础模型与清楚的下一步，不把后续计划写成完成项。四周版本也允许结论为“复杂模型/复核策略没有稳定改善”。

## PySpark 与计算资源

先在小样本验证逻辑，再处理实际可承受的完整数据。允许抽样训练，但报告训练规模与处理规模两种计数。不得复制行凑“大数据”，不得预设 Spark 比 pandas 更快。

本地 Spark 只能证明本地 PySpark 使用。若之后实际跑 EMR Serverless，则记录服务、worker/executor、时长与费用后再描述为分布式执行；不要写成自行管理的 EMR 集群。花费预算尚未设定，当前不创建付费资源。

## 用户应能解释的内容

1. 一行数据表示什么，四种标签从哪里来？
2. 为什么按查询划分，为什么不能在测试集调模型？
3. 简单基线与训练模型各做了什么？
4. 哪一种错误值得检查，复核指标的分母是什么？
5. 哪些 join/groupBy/SQL 由 Spark 完成，实际在哪运行？
6. 哪些结果只属于离线实验，若上线应怎样验证？

## 完成标准

每一项公开数字都能追溯至数据、配置和运行记录；第三方贡献可追溯；用户能用普通语言解释方法与限制。求职故事来自实际做过的独立工作，不等同于过去雇主的工作经历。
