## 1. 先把这个项目讲成一个工作问题

假设你在电商搜索质量团队工作。用户输入搜索词，系统返回一批商品。团队已经有一个相关性分类模型，但没有足够的人力检查它的每一个判断。产品负责人希望知道：模型把哪些商品过于乐观地称为“完全匹配”？如果只能复核其中一小部分，如何安排检查顺序？

本项目把这个问题拆成两步：先训练一个四分类模型，再在它预测为 Exact 的同一批商品配对中，比较随机抽查和按模型不确定性优先抽查。分类回答“模型怎么看这个配对”；复核策略回答“有限的检查预算先用在哪里”。

项目使用已有人工标签做离线评分。它能支持质量监测方案，不能直接计算真实购买转化、收入增长或节约工时。模型没有在 Amazon 线上运行，也没有替真实运营人员修复商品。

你需要掌握的主线是：

> 搜索词与商品 → 核验数据和关联 → 按查询划分 → 提取匹配信号 → 学习分类 → 固定模型 → 安排复核 → 解释收益与限制。

**阅读顺序。** 第一遍只读各章的直观解释和例子；第二遍对照仓库中的实现与报告；第三遍完成最后一章的口头练习。能解释一次 join 为什么会把行数放大，通常比记住十个 Spark 配置名更有用。

**本手册中的状态约定。** “合成教学示例”是为讲解设计的数据，不能用于简历；“已验证结果”必须有实际运行文件；“未来线上方案”表示尚未实施。本手册第 14 章集中记录实际运行证据，避免把教学数字误认为结果。

## 2. 一行数据是什么？四种标签是什么意思？

一行数据是**一个搜索词与一个候选商品的配对**。同一个搜索词可对应多个商品，同一个商品也可对应不同搜索词。不能把每行称为一个用户、一次购买或一条独立搜索流量。

ESCI 的四类标签是发布者的人工相关性判断。E（Exact）表示符合查询意图，S（Substitute）是可替代商品，C（Complement）是配套商品，I（Irrelevant）是无关商品。实际界限取决于查询中的用途、属性和约束。[数据论文](https://arxiv.org/abs/2206.06588)

下面五行全部是**人工合成教学示例，未取自数据集，也不是模型预测结果**。

| 搜索词 | 商品标题 | 教学判断 | 理由 |
| --- | --- | --- | --- |
| blue ceramic mug | Blue ceramic coffee mug | E | 物品、材质、颜色均符合 |
| blue ceramic mug | Red ceramic coffee mug | S | 同类用途，但颜色不符；替代是否可接受仍有语境依赖 |
| mirrorless camera | Camera shoulder bag | C | 可与相机配合使用，本身不是相机 |
| mirrorless camera | Cotton bath towel | I | 与需求无关 |
| camera shoulder bag | Camera shoulder bag | E | 同一商品换了查询后，可以从 C 变成 E |

第五行说明，**相关性是商品相对于查询的关系**，不是商品固定的属性。只读商品标题、不看查询的模型，很难完成这个任务。

文字相似也不等于需求一致。“camera bag”和“camera”共享词汇，却可能是配套关系；“red mug”和“blue mug”非常相似，却违反颜色要求。这是基础词汇模型会遇到的真实难题。

初次阅读代码时，先找 `query`、`product_title`、`esci_label` 三列，再看其他字段。`example_id` 用于追溯一行，`query_id` 用于分组，`product_id` 用于关联。ID 本身不是商品意义的解释。

**自测。** 如果把上述五行随机打散训练和测试，“mirrorless camera”同时出现在两边，会让我们对哪一种泛化能力过于乐观？答案是对未见查询的泛化能力；第 9 章会解释如何处理。

## 3. 为什么先检查两张表，而不是立即训练？

原始数据把配对与商品信息分开存储。配对表回答“哪个查询对应哪个商品、发布标签是什么”，商品表回答“这个商品的标题和属性是什么”。本项目按 `(product_locale, product_id)` 关联，先保留配对表的所有行，再检查缺失商品。[官方文件说明](https://github.com/amazon-science/esci-data)

可以把关联想成查字典：每个配对拿着市场和商品编号，查找对应标题。正确前提是这个“字典”的键唯一。如果商品表同一键出现两条记录，配对可能被复制成两行。

**合成教学示例：**配对表有 100 行，其中 10 行都引用商品 A。如果商品表的 A 被重复存了两次，left join 后会得到 110 行。多出的 10 行来自重复关联，不代表多了 10 条观察。训练前发现它，比训练后解释异常成绩容易得多。

需要留下四类证据：

| 检查 | 能发现什么 | 对结果的影响 |
| --- | --- | --- |
| 商品键是否唯一 | 重复或冲突元数据 | 防止一对多扩行 |
| 关联前后行数 | 隐式丢行或扩行 | 确认分析分母 |
| 未匹配商品数量 | 配对缺少对应元数据 | 决定缺失处理 |
| 空标题及重复配对 | 信息不足、重复观察 | 防止模型与指标被扭曲 |

`left join` 保留左表，即使右表没匹配也留下该配对；`inner join` 会直接删除未匹配行。前者让数据问题可见。左右表重复键都不会被 join 自动修好。[PySpark join API](https://spark.apache.org/docs/3.5.7/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.join.html)

源文件的 SHA-256 是“这次用了哪个文件”的指纹。它不能证明标签正确，却能帮助另一人核对输入完全一致。行数、文件版本、哈希与排除规则合在一起，才形成可复现的数据来源记录。

## 4. PySpark DataFrame 与 Spark SQL 在做什么？

DataFrame 可直观理解为“带有列名和类型、由 Spark 管理的一张表”。你写 Python 表达筛选、关联和聚合，Spark 决定怎样执行。Spark SQL 是用 SQL 表达同样的表操作，二者使用相同的执行引擎。SQL 写法不会自动比 DataFrame 写法更快。[Spark SQL 与 DataFrame 官方说明](https://spark.apache.org/docs/3.5.7/sql-programming-guide.html)

在本项目中，`filter` 选出美国英语和大版本数据，`select` 保留需要的列，`join` 补充商品字段，`groupBy` 汇总类别或错误。每个操作都应对应一个明确的数据问题。

下面是**教学片段**，展示语义；项目实际命令以 README 中已验证的命令为准：

```python
us_pairs = examples.filter(
    (examples.product_locale == "us") &
    (examples.large_version == 1)
)
us_pairs.createOrReplaceTempView("us_pairs")
```

```sql
SELECT esci_label, COUNT(*) AS pair_count
FROM us_pairs
GROUP BY esci_label
ORDER BY pair_count DESC;
```

这段 SQL 回答的是“当前范围内各标签有多少配对”。它没有回答“用户最常搜什么”，因为配对数不是流量。一个查询有更多候选商品，并不意味着更多人搜过它。

Spark 的 schema 是列的数据类型说明。例如 `query` 是字符串、`large_version` 是布尔或数值标记。实际类型必须读取后确认，不能只凭文件名猜测。null、空字符串和不存在的商品匹配是三个不同的问题。

原始文件使用 Parquet，它按列组织并保留 schema。只取标题、标签和键时，列式读取可以减少不必要的数据读取；收益仍取决于文件布局和运行条件。[Spark Parquet 文档](https://spark.apache.org/docs/3.5.7/sql-data-sources-parquet.html)

**面试表达。** “我用 Spark SQL 核对了关联与标签分布，并把每个聚合的分母写清楚。”比泛泛说“熟悉大数据 SQL”更具体。

## 5. 惰性执行：写完一行代码，不代表已经算完

你可以把 Spark 想成一位先接收完整工作清单、再安排执行顺序的助手。`filter`、`select` 等 transformation 通常先建立计算计划；`count`、`show`、写出文件等 action 才触发实际计算。这样的惰性执行允许 Spark 把多个步骤合并或重新安排。[PySpark DataFrame 快速入门](https://spark.apache.org/docs/3.5.7/api/python/getting_started/quickstart_df.html)

例如，先写“读取商品表”，再写“只要美国商品”，再写“只要编号与标题”。Spark 可以利用这些要求，尽量避免搬运无用的列和数据。具体有没有做到，要查看执行计划，不能单靠代码行顺序断定。

这也解释一个常见误会：创建一个变量几乎不耗时，不表示处理百万行只用了几毫秒。如果只计创建 DataFrame 的时间，可能主要测到了计划构造。项目应记录实际 action 完成的耗时，并区分冷启动、读取、特征处理、训练和评估。

`explain("formatted")` 可以查看计划。初学者先找三个词：`Scan` 表示读输入，`Filter` 表示过滤，`Exchange` 往往表示需要重分配数据。计划是理解任务的工具，不要求你一开始就读懂每个节点。[DataFrame.explain 文档](https://spark.apache.org/docs/3.5.7/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.explain.html)

如果多次使用同一个昂贵的中间结果，可以考虑 `cache`。它相当于把算出的内容暂存起来供后续 action 复用；调用 `cache` 本身通常不等于缓存已经被填满。缓存占用资源，用完要释放，缓存所有东西不等于优化。[DataFrame.cache 文档](https://spark.apache.org/docs/3.5.7/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.cache.html)

**一个实用习惯：**查看少量行用 `show` 或有限的样本；大表的 `collect()`、`toPandas()` 会把所有结果汇集到 driver，可能耗尽内存。生成图表时，先在 Spark 中汇总成很小的指标表，再转换为本地数据。[DataFrame 快速入门](https://spark.apache.org/docs/3.5.7/api/python/getting_started/quickstart_df.html)

## 6. Partition、shuffle 与 join：为什么有时会慢？

**Partition** 是一部分数据的处理单位。假设有一大箱卡片，分成若干小叠，不同任务可并行处理。分区数不是机器数；一台电脑也可以有多个分区，多个任务也可能先后使用同一核心。

筛选一张卡片是否属于美国市场，通常只需看卡片本身。按商品编号汇总，或让配对卡与商品卡相遇，则可能需要把相同键的数据放到一起。这种跨分区重新分配就是 **shuffle**。它会增加排序、序列化、磁盘和网络相关开销；本地运行没有跨机器网络，但重排成本仍然存在。[Spark RDD 指南：shuffle 背景](https://spark.apache.org/docs/3.5.7/rdd-programming-guide.html#shuffle-operations)

**合成教学场景：**四叠配对卡里都含商品 A。要按商品聚合，Spark 需要把相关信息送到负责 A 的任务。如果 A 的记录远多于其他商品，某个任务会特别慢，称为数据倾斜。增加分区数未必解决一个超大键的问题。

join 有不同实现。当一边足够小时，Spark 有时会把小表发送给各个处理任务，这叫 broadcast join，可以避免为了匹配两边而做某些大规模重排。小表需要能被相关进程容纳，不能凭“商品表看起来小”就强制广播。[Spark SQL 性能调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html)

本项目的合理优化顺序是：先检查实际数据大小，再尽早筛选范围和列，确认关联正确，查看执行计划与任务耗时，最后才调分区或缓存。未经对照测量，不宣称某个设置提高了速度。

还要区分两种“分区”：计算时的 partition，是任务处理的数据块；磁盘上 `locale=us/` 这类目录，是文件表的分区布局。二者有关，但不是同一个概念。[Parquet 分区发现](https://spark.apache.org/docs/3.5.7/sql-data-sources-parquet.html#partition-discovery)

**自测。** 为什么“把分区数从 8 改成 800”不一定更快？因为调度更多任务需要开销，分区太小浪费调度时间，且瓶颈可能是单个热点键或内存，而非并行度。

## 7. 本地 Spark 证明了什么？以后怎样迁移到集群？

Spark 应用中，driver 负责协调工作和维护计划，executor 执行任务并保存工作数据。集群管理器负责为应用安排资源。PySpark 是 Python 与 Spark 交互的接口；项目使用 Python 并不意味着所有 SQL 运算都逐行在 Python 解释器里执行。[Spark 架构概览](https://spark.apache.org/docs/3.5.7/cluster-overview.html)

`local[4]` 表示在本机使用四个工作线程；`local[*]` 使用本机可用逻辑核心。它们适合开发和学习，但没有提供“多台云服务器协作”的经验证据。[Spark 应用提交文档](https://spark.apache.org/docs/3.5.7/submitting-applications.html#master-urls)

| 可以由本地项目证明 | 仍需单独做过才可证明 |
| --- | --- |
| 使用 PySpark DataFrame、Spark SQL 与 Parquet | 云集群部署和资源管理 |
| 处理真实规模的数据并核对关联 | 多机器执行、网络传输与节点故障处理 |
| 看懂分区、shuffle 和执行计划 | AWS 权限、S3 与 EMR 的实际运维 |
| 可复现的特征与模型流程 | 生产吞吐、在线延迟与成本承诺 |

因此，简历可以写实际处理规模和本地 PySpark 工作，且标明 local execution。迁移到云端需要数据路径、权限、资源和费用约束；不能把更换一个配置项说成已经掌握云运维。

Spark 自带监测界面和事件日志可帮助查看作业、阶段、任务与执行器。它们是执行证据，也帮助判断时间花在哪里。不要把“启动了 SparkSession”当成所有处理已经完成的证据。[Spark 监测文档](https://spark.apache.org/docs/3.5.7/monitoring.html)

本地数据量也可能由 pandas 或其他工具处理。采用 Spark 的学习价值在于实际运用其表处理方式、执行计划与可迁移流程；工具选择的质量应结合可维护性和实测成本判断，不以声称“只有 Spark 才能处理”作包装。

## 8. 从文本到模型：先让每个特征能解释

本次模型实际使用 17 个数值特征：查询/标题词数、共享词数、两侧覆盖率、Jaccard 重合度、完整标题或短语匹配、品牌/颜色词重合与匹配、是否含数字及数字不一致，以及标题/品牌/颜色缺失。每项只读取当前配对的查询与商品字段，不读取标签、ID 或其他配对的答案。

**合成教学示例：**`blue ceramic mug` 有三个不同词，`blue ceramic coffee mug` 覆盖了这三个词，所以查询词覆盖率为 3/3 = 1。`camera bag` 与 `camera` 的重合却不能告诉我们商品是本体还是配件。词汇特征提供信号，但不能完整理解语义。

多数类基线总是预测训练集最常见的标签，帮助判断模型是否比“总选最常见答案”更有用。它简单，却能揭露类别不平衡：如果某类占多数，accuracy 高并不意外。

多项逻辑回归为每一类计算一个特征加权分数，再把各类分数转成概率。直观上，它从训练数据学习：重合度较高、数字匹配等组合与各标签怎样相关。线性模型的可解释性有条件：相关的特征、尺度和正则化都会影响系数，系数不是因果效果。[Spark 分类算法说明](https://spark.apache.org/docs/3.5.7/ml-classification-regression.html#multinomial-logistic-regression)

Spark ML 中，`Estimator.fit()` 学习参数，得到已拟合的模型；`Transformer.transform()` 把输入转成输出。Pipeline 将多个步骤按顺序组织。它有助于复现训练时与预测时相同的处理方式，但把全量数据传给 `fit` 仍然会泄漏，Pipeline 不会替人判断数据边界。[Spark ML Pipeline 文档](https://spark.apache.org/docs/3.5.7/ml-pipeline.html)

本次 Pipeline 实际为 VectorAssembler → StandardScaler → 多项逻辑回归。标准化和分类器只在训练集拟合。开发期比较普通训练与逆类别频率加权：后者让少数类别的错误在损失函数中更受重视，并在验证集 macro-F1 上胜出。它也改变了模型分数的概率含义。固定的文本清理与词重合不需要拟合；数字特征不理解单位或兼容性，不能当作真实不兼容的证明。

**要能回答：**模型到底学到了参数，还是只是用了人写的规则？词重合是人定义的输入，分类器的权重由数据学习。两者在项目中的责任不同。

## 9. 训练、验证、测试：为何要按查询分组？

训练集用来学模型参数；验证集用来比较特征、正则化和复核政策；测试集在这些选择固定之后，提供最终留出的评价。反复看测试成绩再改模型，会使测试集逐渐变成开发资料。[scikit-learn 数据泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)

同一查询的候选商品共享需求和上下文。假设 `blue ceramic mug` 的一些配对在训练集、其他配对在测试集，模型评估的主要问题就不是“遇到一个新查询是否好用”。本项目保留官方测试成员，只从官方训练查询中产生验证集，并审计查询 ID、标准化查询文字及重复配对的重合。

分组划分的直觉是先分“整套题”，再分题里的小问。一个查询组只能进入训练或验证中的一边。分组比例通常针对组而非行，每组大小不同，所以最后行数比例未必刚好是设定比例。[GroupShuffleSplit 官方说明](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupShuffleSplit.html)

| 情况 | 为什么需要注意 | 本项目处理原则 |
| --- | --- | --- |
| 相同 query ID 跨集合 | 同一查询可能被拆散 | 训练前审计并记录策略 |
| 不同 ID 但查询文字相同 | 仅审计 ID 会漏掉重合 | 同时审计标准化文字 |
| 同一商品出现在不同查询 | 改变新商品泛化难度 | 报告已见/未见商品切片 |
| 把标签或 split 放入特征 | 模型偷看答案或集合身份 | 明确禁止 |
| 用测试结果挑阈值 | 过度适应最终评估资料 | 阈值在开发阶段冻结 |

重复商品并不自动等于标签泄漏，因为它面对不同查询可能有不同标签；不过，测试商品是否在训练出现会影响任务难度，应该报告。

看过测试错误后仍然可以学习和改进，但改进后的同一测试成绩应称为探索性结果。新的确认性结论需要新的、尚未参与选择的留出数据。

## 10. Accuracy、precision、recall、macro-F1 怎样直观理解？

Accuracy 是所有配对中预测正确的比例。Precision 问“被我称为这一类的条目中，有多少真的属于这一类”；recall 问“实际属于这一类的条目中，我找到了多少”。F1 用一个数综合 precision 与 recall，二者失衡时会受到惩罚。[scikit-learn 分类指标说明](https://scikit-learn.org/stable/modules/model_evaluation.html#classification-metrics)

**合成教学数字，不是项目结果：**模型说 100 个配对是 E，其中 70 个发布标签是 E，因此 E precision = 70/100 = 70%。测试集实际有 140 个 E，模型识别到 70 个，所以 E recall = 70/140 = 50%。E F1 = 2 × 0.70 × 0.50 / (0.70 + 0.50)，约为 58.3%。

Macro-F1 分别计算 E、S、C、I 的 F1，再给四类相同权重求平均。这样少数类别不会因为行数少而被多数类别完全掩盖。它仍然是模型指标；不同类别对真实业务的损害未必相等。

混淆矩阵每一格记一种“实际标签 → 模型预测”的组合。本项目特别关注 S→E、C→E、I→E：这些都是误判为完全匹配，但潜在业务问题不同。S 可能仍满足相近需求，C 是配套商品，I 是无关商品。

Spark 的内置 `MulticlassClassificationEvaluator(metricName="f1")` 不能未经核对便写成 macro-F1。项目应固定四类集合，逐类算分并取普通平均，同时明确零分母处理。[Spark 多类评估 API](https://spark.apache.org/docs/3.5.7/api/python/reference/api/pyspark.ml.evaluation.MulticlassClassificationEvaluator.html)

展示指标时同时给出支持数：某切片只有少量 C 类案例，C recall 的变化可能很不稳定。一个总体平均数不足以指导运营；类别混淆、候选池规模和复核效果需要一起看。

**自测。** 如果模型将所有配对都预测为 E，E recall 可能很高，其他类别 recall 为零；即使 accuracy 看起来尚可，也没有完成有用的四分类。

## 11. 模型概率与“先检查谁”

模型为每个配对输出四个概率，例如 E=0.52、S=0.36、C=0.08、I=0.04，预测取最高的 E。另一条可能是 E=0.94。两条都进入 predicted-Exact 池，但前者对 E 的支持较弱。

本项目的基础复核政策按 `1 − p(E)` 从大到小排序，只在同一个模型预测为 E 的候选池中选择。分数相同时必须有固定、与标签无关的处理顺序，才能重跑出相同清单。

概率 0.8 不保证现实中“十条必有八条正确”。本次选中的模型使用类别加权，输出分数尤其不能直接当作原始类别分布下的准确概率；当前将它作为排序信号，未做概率校准。校准评价的是一批预测概率相近的样本，其实际频率是否与概率相符；它需另用开发资料验证。[scikit-learn 概率校准说明](https://scikit-learn.org/stable/modules/calibration.html)

**合成教学例子：**固定候选池有 1,000 条 predicted-Exact，其中 200 条发布标签不是 E。预算为候选池的 10%，所以检查 100 条。若某政策选中的 100 条中有 45 条错误：

| 名称 | 计算 | 直观意义 |
| --- | --- | --- |
| Audit yield | 45/100 = 45% | 每检查 100 条，发现 45 条标签不符 |
| Error recall | 45/200 = 22.5% | 找到了全部候选池错误的 22.5% |
| 未检查池错误率 | (200−45)/(1,000−100) ≈ 17.2% | 余下条目中仍有多少错误 |

随机抽查在这个例子中的期望 yield 是 20%，但某一次实际抽样可能上下波动。公平比较必须固定同一个池、同一个检查条数，再报告随机波动和按查询分组的不确定性。

不能用真实标签筛出最容易展示的 100 个错误后称为复核政策；那是在答案已知时选样。标签只在选完之后用于评分。这里的“发现”是离线模拟，并不表示人工已经修复了 45 条。

## 12. 为什么要报告不确定性与错误切片？

测试集是一个具体样本，不是所有可能查询。同一查询里的配对还相互关联：某种需求理解错了，可能同时误判多件商品。把每行都当作独立观察，会低估部分不确定性。

本项目按查询组重采样：每次抽取若干完整查询，带上其全部配对，再重新计算指标。重复后观察结果范围。这是针对当前数据和已固定模型的稳定性检查，不能证明未来商品、季节或用户偏好改变后仍然一样。

对于复核策略差值，在同一次重采样资料上比较两个政策，有助于让二者面对同一组查询。每次重采样的候选池、预算取整及重排序规则必须固定并记录。区间窄不代表没有系统性偏差；有偏的数据也能产生很稳定的数字。

切片把平均数拆成可解释的问题。例如含数字查询，可能涉及尺寸或型号；缺失品牌，可能减少一个匹配线索；未见商品，检验对新商品的表现。切片应在正式测试前定义，避免看见哪里表现最差才临时选择并当作确认性发现。

人工阅读错误帮助解释原因。你可以记录“型号冲突”“配件与本体混淆”“缺少属性信息”“发布标签可能有歧义”。如果专门挑了难例，难例比例就不能当作总体错误率。AI 辅助说明也不能冒称已经完成了独立人类标注。

对发布标签有疑问时，保存原标签，另记意见和理由；不直接覆盖它并重新计算更好看的成绩。单人复核能提供定性观察，但不能报告多标注者一致性。

**可采取的运营判断。** 如果某类错误数量充足、重复出现、规则解释清楚，就可以建议小规模专项复核；若样本少、区间宽或标签含糊，建议应先增加证据。这里的建议是基于项目设计的推论，实际是否成立要看第 14 章结果。

## 13. 怎样把离线结果转成产品和运营建议？

好的建议要同时说明**采取什么行动、依据是什么、还缺什么验证**。例如“在质量抽检中先检查模型较不确定的 Exact 判断”是一项可执行的候选政策；是否值得采用，要看等预算收益、遗漏的错误和稳定性。

| 如果结果显示…… | 可以考虑的行动 | 仍需要验证的内容 |
| --- | --- | --- |
| 不确定性排序稳定多发现错误 | 对复核队列做小规模试点 | 人工实际耗时、判断一致性 |
| 数字查询经常发生型号混淆 | 检查数字/型号字段与约束 | 规则是否误伤真实替代品 |
| C→E 错误集中在配件 | 建立本体/配件专项检查 | 标签边界是否清楚 |
| 更多检查的边际收益下降 | 按资源讨论预算曲线 | 真实人工成本与错误损害 |
| 策略与随机抽查差异不稳定 | 保留随机抽查并继续收集证据 | 分数、样本及标签问题 |

这些是**读结果的模板，不是本项目已经观察到的结论**。基准里没有流量权重，也没有点击、购买、订单价值，所以不能把每条错误当作同等收入损失，更不能把“相对抽查收益”改写成“转化率提升”。

若将来试点，先把运营过程测量好：完成一条复核要多久，哪些错误需要进一步处理，处理后是否改善用户看到的内容。抽检程序还应保留一部分随机样本，帮助观察整体问题；只看模型选中的难例，会失去代表性。

真正上线搜索变更时，可设计面向用户或会话的随机实验，事先约定搜索成功相关指标与延迟等保护指标。具体随机化单位取决于产品如何曝光和产生交互，不能从这个离线数据集直接确定。当前项目只提供未来实验设计思路。

求职时可以这样组织故事：团队面临有限检查预算 → 我定义观察单位与错误 → 建立可追溯的 Spark 流程 → 比较基础模型和复核政策 → 给出有证据的建议及上线前验证要求。数据管道、模型和产品判断在同一条逻辑上。

## 14. 本次实际实现与结果快照

**状态：已验证，本地 MVP。** 以下数字直接核对 `reports/data_audit.json`、`reports/validation_metrics.json`、`reports/test_metrics.json` 和 `experiments/frozen_study.json`。前面的教学数字不参与这里的计算。

环境为 Python 3.11.15、Java 17.0.20.1+1、PySpark 3.5.7；macOS arm64，使用 `local[4]`，driver 内存 4 GB。数据固定到上游 revision `7916cdf6ab75a462e77f20ab40428a10923998d5`，每个源文件哈希和划分哈希已记录。

读取了 2,621,288 条多市场配对，实际分析 US 大版本 1,818,825 条；US 商品元数据为 1,215,854 行。商品键和配对 ID 无重复，关联无丢失，无空标题。官方训练与测试之间发现一个查询 ID/标准化文字重合，保留全部官方测试，从训练侧移除该查询的 3 行。

| 集合 | 配对数 | 查询数 |
| --- | ---: | ---: |
| 训练 | 1,113,987 | 59,947 |
| 验证 | 279,073 | 14,940 |
| 测试 | 425,762 | 22,458 |

**模型选择。** 固定 17 项词汇特征和正则化参数后，在开发资料上比较普通逻辑回归与类别加权版本。验证集 macro-F1 分别为 0.2593 和 0.3340，选中加权版本。模型、数据和配置均在正式测试前冻结。

| 最终测试指标 | 多数类基线 | 选定模型 |
| --- | ---: | ---: |
| Macro-F1 | 0.1972 | 0.3334 |
| Accuracy | 65.14% | 48.82% |

模型 macro-F1 的 95% 查询组 bootstrap 区间为 [0.3302, 0.3367]，共 300 次重采样。Accuracy 下降不能隐藏：E 类占测试集 65.14%，全猜 E 就能达到该 accuracy。加权模型扩大了对其他类的识别，却增加了部分总体错误；“模型更好”必须说清依据的是哪项指标。

| 类别 | Precision | Recall | F1 | 支持数 |
| --- | ---: | ---: | ---: | ---: |
| E | 80.13% | 57.78% | 0.6715 | 277,348 |
| S | 36.42% | 21.63% | 0.2714 | 95,054 |
| C | 4.17% | 22.20% | 0.0703 | 10,922 |
| I | 22.14% | 58.02% | 0.3205 | 42,438 |

C 类的 precision 只有 4.17%，表明当前词汇模型很难可靠识别配套关系。本模型适合展示可复现评估和复核优先级研究，不能据此自动进行商品下架、惩罚或正式搜索排序决策。

**运营相关结果。** 固定模型产生 199,989 条 predicted-Exact，占测试配对 46.97%；其中 39,729 条发布标签不是 E，错误率 19.87%。对同一个池进行等预算比较：

| 预算 | 选择条数 | 优先策略发现错误 | 优先策略 yield | 随机抽查期望 yield |
| --- | ---: | ---: | ---: | ---: |
| 5% | 9,999 | 3,386 | 33.86% | 19.87% |
| 10% | 19,998 | 6,575 | 32.88% | 19.87% |

10% 预算下，随机抽查期望发现 3,972.72 条错误；优先策略的 yield 约为其 1.66 倍，差值为 13.01 个百分点，95% 查询组 bootstrap 区间为 [12.11, 14.01] 个百分点。这里与随机策略的**期望**比较，另用 100 次随机抽样展示波动；小数的期望错误数不代表实际检查了部分条目。

这支持“优先检查模型较不确定的 Exact 判断”的试点建议，但错误召回只有 16.55%。未检查的 179,991 条里仍有 33,154 条错误，剩余错误率 18.42%。检查高风险部分后，不能把余下池视为已合格。

优先策略只用 `p(E)` 排序，分数相同时按 example ID 固定顺序；标签在选择之后才用于评分。这是公开标签支持的离线模拟：没有真实完成 19,998 次人工复核，没有 AWS、线上曝光、工时或营收测量。

**执行证据。** 1,944 行小样本流程、9 项 Spark 检查和 14 项评估检查已通过。数据准备 40.71 秒、训练及开发评估 14.629 秒、测试评估记录 2.344 秒是单次本机阶段观测，不包含全部下载和 Java 启动成本，不能用来宣称 Spark 的跨工具性能优势。

训练和特征处理在 Spark 中执行；为本地指标、bootstrap 和画图，程序把有限列的验证/测试预测表转换为本地 pandas/NumPy 数据。当前规模可运行，但这种本地汇集限制了后续扩展，需要随数据增长重新设计。

## 15. 用七个练习确认自己真的理解了

每题先用自己的话回答，再对照提示。无需背诵答案；面试时最有价值的是能解释选择及后果。

1. **30 秒讲清观察单位。** 提示：一个查询—商品配对；重复查询和重复商品都可能正常；行数不是用户数。
2. **解释 join 后为什么多出行。** 提示：检查右表键唯一性；一个配对可能匹配多个商品记录。回答中说出实际使用的两个关联键。
3. **解释 Spark 何时开始算。** 提示：transformation 建计划，action 触发计算。举出本项目的一个 action，并说明为什么不能只计创建变量的时间。
4. **解释一个 shuffle。** 提示：按键聚合或某些 join 需要把相关数据重新放到一起。说明本地也有重排成本。
5. **解释四分类与复核政策的区别。** 提示：模型固定后，政策选择先检查哪些 predicted-Exact；不能拿两个不同候选池的 yield 直接比较政策优劣。
6. **口算两个分母。** 合成题：检查 80 条，发现 24 条错误，池中总共 120 条错误。yield=30%，error recall=20%；不能说“整体质量提高 30%”。
7. **描述一个真实限制。** 提示：没有真实流量、成本或行为结果；本地运行不是云集群；词汇模型缺少语义理解。选一个并解释它怎样限制建议。

**不看代码的小挑战。** 为“搜索词含型号、商品标题型号不一致”的情况提出一个特征；说明该特征能在预测时获得，且没有用到标签。再解释为什么它可能误伤某些兼容配件。

**看代码的小挑战。** 找到实际实现中一处 join、一处 SQL 聚合和一处模型训练；用普通话逐句讲出输入、输出、单位和验证方式。若讲不清，先让 Codex 帮你在五行合成数据上演示，再回到真实文件。

**面试故事的表达范围。** 可以说明自己定义了问题、检查了数据、用 Codex 辅助实现并核验结果。只能用已验证的本项目数字；不得把独立项目放进过往雇主经历，也不要把计划中的 AWS 工作写成完成项。
